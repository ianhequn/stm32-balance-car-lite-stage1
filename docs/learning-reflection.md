# 我的项目理解、经历和复盘

## 一开始我以为这个项目只是“把小车调站起来”

刚开始做这个项目时，我对两轮自平衡小车的理解比较直接：MPU6050 测角度，PID 算输出，电机转起来，小车就能站住。

真正做下来以后，我发现这个项目不是单纯写一个 PID，而是一个完整的嵌入式控制系统。它至少包含这些部分：

- 传感器采集：MPU6050、编码器、超声波
- 姿态解算：加速度计、陀螺仪、互补滤波
- 执行控制：PWM、电机方向、TB6612FNG
- 闭环控制：角度环、速度环、方向差速
- 状态管理：遥控模式、跟随模式、避障模式
- 调试观察：串口地面站、OLED、手机 App 日志
- 工程实现：CubeMX 配置、Keil 编译、烧录、上板测试、GitHub 归档

这让我意识到，嵌入式项目的难点不是某一段代码，而是很多模块必须按正确的节奏一起工作。

## 我对控制链路的理解

现在我对这个小车的核心理解是：

两轮自平衡小车本质上是在不断“摔倒”和“救回来”。车身只要稍微前倾，控制器就要让轮子往前追；车身往后倒，轮子就往后追。这个过程靠角度环完成。

但只有角度环还不够。小车可能会越跑越远，或者因为地面摩擦、电机差异、安装偏差导致一直漂移。所以还需要编码器形成速度反馈，用速度环限制整体移动趋势。

我现在把它理解成：

```text
角度环负责不倒
速度环负责不乱跑
转向差速负责左右转
模式管理负责什么时候听谁的命令
```

最终电机输出不是某一个模块直接决定，而是几个控制量叠加后的结果：

```text
电机输出 = 角度环输出 - 速度环输出 ± 转向差速
```

这个理解对我很重要，因为后面调参时不能只盯着一个变量。静止抖动、加速过快、停止不明显，可能分别来自机械零点、角度环、速度环、积分残留、蓝牙命令逻辑。

## 项目中遇到的主要困难

### 1. 教程代码和本地工程不同步

一开始最大的问题是：Notion 教程是一步一步来的，但本地工程不一定正好停在同一步。

比如速度外环、超声波、OLED、蓝牙这些内容都涉及多个文件：

- `control.c/h`
- `main.c`
- `stm32f1xx_it.c`
- `tim.c/h`
- `usart.c/h`
- `gpio.c/h`
- 新增模块文件

只复制某一段代码是不够的，因为外设初始化、中断回调、全局变量、Keil 工程文件都要一起同步。

这个过程让我学到：嵌入式工程不是“代码片段集合”，而是由 CubeMX 配置、HAL 初始化、中断、主循环、模块接口共同组成的系统。

### 2. 不知道小车内部到底有没有收到数据

做蓝牙遥控时，手机 App 日志显示已经发送命令，但小车一开始没有明显反应。

这个问题不能靠猜。后来我们在 OLED 上加了：

```text
BT  :F     3
```

用来显示最后收到的蓝牙字符和接收次数。这样一看就知道：

- App 有没有发出去
- STM32 有没有收到
- USART3 中断有没有正常进入
- 协议解析有没有执行

这个经历让我理解到：调试系统时，最重要的是先把内部状态暴露出来。没有可观测性，就只能凭感觉乱试。

### 3. 速度环和角度环不是越大越好

调参时我明显感受到：参数不是越大越灵敏。

角度环太弱，小车站不住；太强，又会抖。速度环太弱，遥控没反应；太强，又会一直加速或刹不住。速度积分太大，静止时也可能产生残留输出。

现在我对调参的理解是：

- 先保证电机方向和编码器方向正确
- 再保证角度环能基本站住
- 再加入速度环控制漂移
- 最后调遥控速度和转向手感

不能一上来就同时改很多参数，否则根本不知道是哪一个参数造成了变化。

### 4. “停止”和“后退”不是简单发一个字符

蓝牙遥控一开始是单字符协议，按一下 `F` 小车就保持前进目标。这样会导致一个问题：它不是临时前进，而是持续追速度目标，所以看起来会一直加速。

后来把 App 改成：

```text
按下方向键：发送 F/B/L/R
松开方向键：自动发送 S
```

这让我理解到，嵌入式系统的人机交互也很重要。不是通信通了就算完成，还要让控制方式符合真实使用场景。

### 5. 提起识别和手动遥控会互相影响

加入提起/着陆识别之后，小车被拿起来会关电机，这是安全功能。但蓝牙遥控时，如果保护状态没有处理好，可能出现“手机发了命令但电机不动”的感觉。

所以我们做了一个折中：蓝牙命令来了以后清除异常空转锁定，但角度超过安全范围时仍然会保护。

这让我学到：实际项目里的功能不是孤立的。一个安全功能可能影响遥控功能，一个遥控功能也可能绕过保护逻辑。工程设计要考虑模块之间的关系。

### 6. APK 打包不是写完代码就结束

做手机 App 时也遇到环境问题：

- 本机没有直接可用的 Java/Gradle 环境
- Gradle 需要 JDK17
- Android 工程路径有中文名导致构建检查报错
- APK 要能直接发到手机安装

最后用项目内便携 JDK17 和本机 Android SDK 打包，避免污染 Python 环境，也没有永久修改系统 PATH。

这让我理解到，软件交付本身也是工程能力的一部分。能写 App 和能交付 APK 是两回事。

## 我学到的东西

### 嵌入式方面

- CubeMX 配置和代码不是分开的，外设配置会直接影响代码能不能跑
- 中断回调是嵌入式系统的关键，例如 SysTick、USART3、TIM1 输入捕获
- 编码器方向、电机方向、PWM 通道一旦错了，PID 再正确也没用
- 串口调试和 OLED 显示能大幅提高排查效率

### 控制方面

- 角度环主要解决“倒不倒”
- 速度环主要解决“漂不漂”
- 速度积分会带来残留，静止抖动不一定是角度环的问题
- 调参要一次只改少量变量，并观察明确现象

### 工程方面

- 一个项目要能复现，就不能只保存源码，还要保存工程文件、APK、说明文档和测试素材
- README 不是装饰，而是别人理解项目的入口
- 视频和截图是作品展示的一部分
- GitHub 仓库结构会影响项目给人的第一印象

### 对我个人的意义

这个项目让我第一次比较完整地经历了一个软硬结合系统从教程、代码、上板、调试、App、文档到 GitHub 归档的闭环。

它还没有完美，速度环和角度环还要继续调，超声波跟随也还能优化。但第一阶段已经让我真正理解了：嵌入式不是只会点灯，也不是只会复制代码，而是要把硬件、传感器、控制算法、通信、人机交互和工程管理连接起来。

这正好符合我后面想走的方向：嵌入式、视觉、边缘 AI、软硬结合的智能系统。
